# P1.3 — `events_to_time_matrix`, the wall-clock builder

Task: P1.3 `[AITU]`. Decisions implemented: D-02, D-04, D-05, D-06.
Date: 2026-08-06. Status: done, with one deviation recorded as I-04.

## 1. What this step is

This is where the refactor becomes real. The 1.x builder needed a tempo, so the same recording
produced different columns depending on a number somebody typed. The new builder takes the events
and the duration, and nothing else.

Three rules decide what reaches the grid, and their order matters:

1. The engine's artifacts are dropped and phantom re-onsets are merged, exactly as before. Both
   judgements need the events in seconds, so they run first.
2. Notes shorter than one frame are refused (D-05).
3. Near-simultaneous onsets are grouped on raw times (D-04), and each group snaps to one column
   (D-02).

The sustain written into the grid is measured from the note's own release (D-06). It is not the
printed length of the note, which is the gap to the next onset in the same hand and is decided in
Phase 3. Those two numbers must never be derived from each other.

## 3. The deviation, in full

**The 1.x builder was kept.** Read literally, this task replaces `events_to_raw_matrix`, and P1.8
asserts that no code path accepts a tempo. Doing that stops the app transcribing, because
`pipeline.py` is only rewired in P4.2. The supervisor reviews this work in the browser, so three
phases with a backend that cannot transcribe is a real cost, and it also removes the chance to
compare new columns against old ones on a real piece.

So `events_to_raw_matrix` is untouched and still used by the pipeline, and the new builder sits
beside it. Both are in the same module, and the docstring says which is which and when the old one
goes. The full detail and the alternative are in [`issues.md`](issues.md) as I-04. **P4.2 deletes the
1.x builder in the same task that rewires the pipeline**, which is where the deletion is safe.

P1.8's no-tempo assertion is therefore written against `events_to_time_matrix`: the test reads the
function signature and fails if a tempo, a BPM or a granularity parameter ever appears on it.

## 4. Other decisions taken inside the task

**The release is snapped on its own, not measured from the group.** A chord shares an onset column
because it is one attack, but its notes do not share a length. Each note's end column comes from its
own release time, so a chord released unevenly keeps that in the grid.

**A note always occupies at least its onset column.** After the sub-frame filter every note lasts at
least one frame, but a note of exactly one frame could otherwise round to an end column equal to its
start. The end is clamped to `start + 1`.

**A whole group past the end of the audio is counted per note, not per group.** `dropped_past_end`
stays comparable with the 1.x report.

**The sub-frame filter uses this piece's frame length**, not a fixed millisecond floor. At 20 ms
frames a 30 ms note is kept; at 40 ms it is not. That is the meaning of D-05.

**No cap on the sustain.** D-06 says the stored sustain is capped at one redonda of the active
ladder, and no ladder exists at this point in the pipeline. That is I-01, still unanswered. The
builder stores the full measured sustain, which is the alternative proposed there and the one that
matches D-03. If the supervisor decides otherwise, the change is one clamp in this function.

## 5. Things I believed that turned out false

I expected to reuse `matrix/approximation.py`'s `snap_note`, since it already places an event on a
grid. It cannot be reused: it snaps with a tolerance, expressed in beats, and rounds the duration to
something expressible in at most two figures. Both of those are the old model, where the column and
the figure were the same thing. The new placement is a plain rounding and does not consult a figure
at all, which is the point.

I also expected the grouping to change the number of onsets in the matrix. It does not: every note
of a chord still gets its own onset cell, in the same column. The grouping decides the column, not
the content.

## 6. Tests

`aitu-backend/tests/test_time_matrix_build.py`, sixteen tests, all passing. The three the plan asks
for in P1.8 are here:

- **No BPM.** The signature is read and fails if any parameter mentions a tempo, a BPM or a
  granularity.
- **Determinism.** The same events in reversed order give an identical grid.
- **Straddle.** Two notes 19 ms apart that snap individually to columns 1 and 2 land in column 1
  together.

The rest cover the sub-frame filter at two frame lengths, the measured sustain, a chord whose notes
are released at different times, a re-strike cutting the first note, a note outside the keyboard, an
onset past the end of the audio, an empty transcription, and the report sentence.

Nothing was deleted. The whole existing suite still passes with the same two pre-existing failures.
Run as described in `P1.1-time-grid.md` §5.
