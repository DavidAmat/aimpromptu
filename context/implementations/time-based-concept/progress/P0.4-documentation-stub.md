## 1. Why a stub is worth writing before the code

The refactor adds around ten modules across nine phases, written by different workers over time. If
each one documents itself when it lands, the field names end up described in ten places and the
reader has to assemble the picture. A stub with the sections already named means each phase fills in
its own section, and anyone reading the tree can see what exists and what does not.

## 3. Decisions taken inside the task

**The stub says which phase fills in each empty section.** An empty heading with no owner reads like
missing documentation. An empty heading that says "filled in by P3.7, when the endpoint exists" reads
like a plan, and it tells the P3.7 worker where its documentation goes without needing a rule.

**`issues.md` was created with an entry format and with the three findings from P0.1 already in it.**
The worker prompt requires the file to exist and requires a worker to stop after writing to it, so an
empty file with no shape would have made the first person to need it invent one under pressure.

**The stub keeps the two-folder rule.** Field names, module paths and endpoint shapes are engineer
detail, so they live in `documentation/`. The reasoning stays in
`context/implementations/time-based-concept/`, and the file opens with the `> Context:` link back up
to it, as `00-documentation-instructions.md` requires.

## 4. Things I believed that turned out false

I expected `context/implementations/00-implementation-index.md` to exist, because
`context/00-index.md` lists it. It does not exist on disk. That is a pre-existing broken link in the
index, unrelated to this refactor, and it was left alone rather than fixed inside this task. It is
worth repairing in P8.5, which owns the index.
