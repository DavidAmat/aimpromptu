# P4.1 — What is stored today, and what a migration can rebuild

Task: P4.1 `[AITU]`. Decisions implemented: none directly; this task exists to protect D-01, D-03
and success criterion 5.
Date: 2026-08-07. Status: done.

## 1. Context

Phase 4 removes the granularity from the storage layer. A granularity is the note figure a matrix
column represented, so it is the thing that made a stored column mean "one sixteenth" instead of
"40 milliseconds of wall clock". Once that value leaves `schemas/naming.py` and `storage/paths.py`,
any file whose meaning depended on it can no longer be read correctly, and any file that cannot be
rebuilt from the raw transcription is lost.

That is why P4.1 runs first, and why nothing else in Phase 4 may start until this list exists. The
plan says so, and `system-prompt-worker.md` §5 repeats it.

The question this task answers is narrow. For every artifact on disk: can the new wall-clock path
rebuild it from the recorded note times, or does it hold work a person did by hand that no rebuild
would invent?

## 2. Method

A script now reads the whole `data/` tree and classifies every artifact:
`aitu-backend/scripts/inventory_artifacts.py`. It only reads. It never writes, moves or deletes a
file, and it uses no third-party library, so it also runs in environments where the backend cannot
be installed.

Run it with `uv run python scripts/inventory_artifacts.py`, or with `--json` for a machine-readable
form, or with `--data DIR` to point it at another tree.

The file names it looks for are written into the script rather than imported from
`transcription/pipeline.py` and `schemas/naming.py`. P4.2 and P4.4 rewrite both of those modules,
and this inventory has to keep reading the tree those modules wrote *before* the rewrite. Six
duplicated strings are cheaper than an inventory that stops working on the day it matters most.

Re-derivability is measured rather than assumed. Section 4.1 describes the check.

## 4. Evidence

### 4.1 The grid really is a function of the recorded notes

"Re-derivable" is the whole basis for saying a file may be replaced, so it was checked rather than
asserted. The recorded notes were read from `events.json`, passed through the current builder
`events_to_raw_matrix`, and the result was compared cell by cell against the stored `raw.npz`.

The two grids are identical: the same shape, 88 by 4966, the same 17655 filled cells, and zero
differing cells.

The comparison also recovered a number that is not written down anywhere. A raw grid's columns
depend on the tempo it was built at, and the working artifact stores the granularity in
`raw-granularity.txt` but never stores the tempo. The stored grid matches a rebuild at exactly
60 BPM, which is the default, so the tempo can be recovered by trying values until the grids match.
It should not have to be. This is a concrete example of the problem the whole refactor exists to
remove: a stored file whose meaning depends on a number nobody recorded.

Under D-01 the question disappears, because a column is 40 milliseconds and no tempo takes part.

### 4.2 The migration is a no-op for this artifact

The wall-clock path already reads `events.json` directly and stores nothing. The report for P2.4 to
P3.8 states this: every request to `/time/{uuid}/peaks`, `/ladder-preview` and `/score` re-derives
from the stored events, and no result is cached or written.

The consequence is that the single artifact in this tree already works on the new path today, with
no conversion step. What P4.5 has to do for it is not "convert" but "stop the old files from being
read as if they still meant something". Those files are the granularity-keyed matrices in section
3.1, and they only matter until P7.11 retires the four older tempo-based tabs that read them.

I have not confirmed this in the browser as part of this task, because P4.1 changes no behavior.
The claim rests on the P2.4 to P3.8 report and on reading `api/time_score.py`.

### 4.3 There is no second copy of the recorded notes

The root `.gitignore` excludes `aitu-backend/data/audio/**` and every `.npz` under `data/`. Only
`data/README.md` and `data/example-scores.json` are tracked by git. So `events.json`, which section
4.1 shows is the source everything else comes from, exists in exactly one place: the local disk of
the development machine.

There is a second `events.json` at `poc-onset-duration-distribution/data/events.json`, and it is
**not** a backup. It holds a different transcription: 2398 notes over 305.37 seconds, titled
"Mr Blue Sky — segment 00:05.00–05:10.37", against 2751 notes over 310.37 seconds in the working
artifact. The two files are useful for comparison and useless as a recovery path for each other.

The practical instruction that follows is short. Before P4.5 writes or deletes anything, copy
`aitu-backend/data/` somewhere outside the repository. Excluding the audio it is about 230
kilobytes, and including the audio about 19 megabytes, so the copy costs nothing and removes the
only irreversible risk in Phase 4.

## 5. The classification, for artifacts that do not exist yet

The tree is nearly empty today, but the same tree will hold real work later, and the migration in
P4.5 has to behave correctly then as well. The script therefore reports four verdicts, and the
reason each one exists is a real code path in the current backend.

**`rederivable`.** The folder has `events.json` and no hand-edit flag. Everything else in it is a
function of that file, as section 4.1 demonstrates. The migration rebuilds it at 40 milliseconds.

**`hand-edited`.** The folder has `raw-edited.flag`. That file is written by `persist_edited_raw`
when a person changes the grid directly, and its meaning is recorded in `pipeline.py`: from that
moment the cells say something the recorded notes do not. Rebuilding would discard the person's
work without telling them. These artifacts must be flagged `needsRederivation` and left alone.
When `raw_before_edit.npz` is also present, the edit survives as the difference between the two
grids, so it is recoverable even if the current grid is replaced.

**`no-raw-events`.** The folder has a grid but no `events.json`, because it was transcribed before
the events were kept or the file was lost. Re-transcribing the audio produces a different set of
notes, not these notes, so it is a new artifact rather than a migration. These must also be flagged.

**`derived-only`.** A saved version under `data/playground/` or a promoted copy under
`data/library/tracks/`. Its `.npz` sits on a beat grid at a stored tempo, which has no meaning under
D-01, so it can only be rebuilt by returning to the audio it came from, and only when its
`metadata.json` records an `audioUuid` whose folder still has `events.json`. The script checks that
link and says which versions have it.

## 6. Hand-written content the migration must carry, not rebuild

A rebuild recreates grids. It does not recreate anything a person typed, and this is the part of the
inventory most likely to be forgotten, because none of it is a matrix.

For a working artifact, the notation settings and annotations live in `notation.json`, and the grid
renderer's annotation envelope lives in `grid-notation.json`, both next to the matrices. For a saved
version, `metadata.json` carries the comment, the key signature, the annotations and the stored hand
map, and `metadata_track.json` carries the version history and the parent pointers between versions.

The script lists these per artifact in a `hand-written` column. In the current tree the column is
empty everywhere, so nothing of this kind is at risk today.

## 7. What reads these files

P4.2, P4.4 and P4.5 each change one part of this storage layer, so it is worth recording which
modules will notice. The list came from searching for callers of the storage helpers in
`transcription/pipeline.py`.

The working artifact's files are read by `api/matrix.py` (the Matrix tab, the hand map, the edit and
export routes), `api/notation.py` (the Notation tab and its re-quantisation banner),
`notation/artifacts.py` (both artifact kinds) and `api/time_score.py`. Of these, only
`api/time_score.py` belongs to the new path, and it reads `events.json` alone.

The saved versions are read by `storage/repository.py`, `storage/promotion.py`, `api/library.py` and
`notation/artifacts.py`. None of them is on the new path.

## 8. Things I believed that turned out false

I expected the inventory to be a list of things needing conversion. It is the opposite. The one
artifact on disk needs no conversion, because the new path never stored anything in the first place
and reads the recorded notes on every request. The dangerous work in Phase 4 is therefore not the
migration itself but P4.2 and P4.4, which delete the code and the folder names the *old* path still
depends on while four tabs are still using it.

I also expected the tempo a raw grid was built at to be recorded somewhere on disk, next to the
granularity that already is. It is not. `raw-granularity.txt` exists precisely because changing the
raw granularity constant silently reinterpreted every stored grid, and the same argument applies to
the tempo with equal force, but only half of the fix was made. This does not need repairing, because
Phase 4 removes both values from the stored form, and repairing it now would be work on the model
being replaced.

## 9. Tests

No test was added. This task adds a read-only reporting script and changes no behavior, and a test
that asserts what happens to be in one developer's `data/` folder would fail on any other machine.
The script's correctness was established by running it against the real tree and comparing its
output with the actual directory listing, and by the cell-level comparison in section 4.1.

The backend suite was run to confirm nothing moved: 832 tests pass, 5 are skipped, and the single
failure is `test_transcription.py::test_changing_the_bpm_reinterprets_the_same_grid`, which P4.8
deletes rather than fixes.

One note for whoever runs the suite next. `test_matrix_pipeline.py::test_hand_inference_does_not_blow_up_on_unplayable_input` failed once and passed on
every later run, including on its own. It is intermittent, not a regression from this task, and it is
worth watching during P4.3, which is the task that touches the hand splitter.
