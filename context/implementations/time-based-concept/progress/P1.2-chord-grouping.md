# P1.2 — `transcription/grouping.py`, chords on raw times

Task: P1.2 `[AITU]`. Decisions implemented: D-04.
Date: 2026-08-06. Status: done.

## 1. Why grouping has to happen before snapping

A chord is one rhythmic event even when the three keys land eight milliseconds apart. Those eight
milliseconds are not a rhythm, and if they are left in the data they dominate the low end of the
distribution of gaps between onsets, which is the plot the user will be asked to read in Phase 7.

Grouping cannot be done by asking "are these notes in the same column". Two onsets 39 ms apart fit
inside one 40 ms column but can fall either side of a boundary, so that question gives a different
answer depending on where the chord happens to sit in the piece. The grouping therefore runs on the
raw float timestamps, and the whole group then snaps together on the group's single start time.

## 3. Decisions taken inside the task

**The window is imported, not repeated.** `DEFAULT_GROUP_WINDOW_MS` is `DEFAULT_ALIGN_WINDOW_MS`
from the schema. D-04 and D-24 are the same 20 ms, and the renderer's copy of that number comes from
the same place, so there is one definition.

**A group is returned, not a start time.** The PoC's `collapse_attacks` returns the group start
times, because the measurement only needed those. The pipeline needs to know which notes belong
together, so `OnsetGroup` carries the events, an index and the start. The index becomes `groupId` in
the score payload.

**Ties are broken by MIDI note.** Two events with identical start times would otherwise be ordered
by whatever the engine emitted, and the grouping would depend on that. Sorting by `(start, note)`
makes the result the same whatever order the events arrive in, which one of the tests asserts.

**A window of zero raises.** It would silently turn every note of every chord into its own attack,
and the symptom would appear much later as a histogram with a large spike near zero.

## 4. Things I believed that turned out false

I believed the non-chaining rule was a small refinement of a normal clustering step. It is the whole
point. With chaining, a run of fast notes 19 ms apart merges into one attack a hop at a time, and a
dense passage collapses into a single chord. The test that holds this is
`test_the_window_is_measured_from_the_first_onset_not_the_previous_one`, and it should not be
weakened.

## 5. Tests

`aitu-backend/tests/test_transcription_grouping.py`, nine tests, all passing:

1. The window is 20 ms.
2. A chord is one attack, and the group reports its spread.
3. Notes further apart than the window are separate attacks.
4. The window is measured from the first onset, not the previous one.
5. A chord that straddles a column boundary is still one attack. The two notes are 19 ms apart and
   snap individually to columns 1 and 2; grouped, they land in column 1 together.
6. The result does not depend on the order the engine emitted events.
7. Groups are numbered in order, so the payload can carry a `groupId`.
8. An empty transcription gives no attacks.
9. A window of zero is refused.
