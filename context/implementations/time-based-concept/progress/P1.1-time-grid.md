# P1.1 — `matrix/time_grid.py`, the frame ↔ millisecond conversion

Task: P1.1 `[AITU]`. Decisions implemented: D-01, D-02.
Date: 2026-08-06. Status: done.

## 1. Why this module exists on its own

The width of a column used to be a calculation involving a tempo, and that calculation was repeated
in several modules. Every copy is a place where the answer can differ, and the frame length is the
one number the whole refactor rests on: if two modules disagree about how long a frame is, the notes
and the ruler disagree about where they are.

So there is now exactly one module that knows a frame is 40 ms, and everything else asks it.

## 3. Decisions taken inside the task

**Halves round up.** D-02 says the column is `round(onset_ms / frameMs)` and does not say what
happens to an onset exactly on a boundary. Python's built-in `round` sends a half to the *even*
column, so two onsets the same distance from a boundary go to opposite sides depending on where they
are in the piece. That is deterministic, so it satisfies success criterion 3, but it is not what a
person predicts. The implementation is `floor(x + 0.5)` and the docstring says so. Changing it later
would move some columns by one, so it is worth the sentence.

**Two different questions have two different functions.** `frame_of_ms` answers "which column is
this instant in" and `frame_span_of_ms` answers "how many columns does this stretch occupy". A note
of 45 ms is one column *long* and starts in column 1. Writing one function for both is the kind of
mistake that produces a note one column too wide at the end of every phrase.

**The frame length is validated where it is set, not where it is used.** `validate_frame_ms` refuses
zero, a negative and an infinity, so a bad value fails at the boundary instead of appearing later as
an empty matrix.

**Negative times raise.** A negative onset is a bug in the caller, and rounding it quietly to column
0 would hide it.

## 4. Things I believed that turned out false

I expected to define `DEFAULT_FRAME_MS = 40` here, since this is meant to be the only module that
knows the frame length. It is already defined in `schemas/time_matrix.py`, where it is the default
value of the envelope's `frameMs` field, and defining it twice is exactly the drift this module
exists to prevent. It is imported from the schema and re-exported.

## 5. Tests

`aitu-backend/tests/test_time_grid.py`, ten tests, all passing:

1. A frame is 40 ms and the seconds per frame follow.
2. An onset snaps to the nearest column, including the 337 ms case from the measurement.
3. A half lands on the later column, at four different places in the piece.
4. The same onset gives the same column every time, with no tempo anywhere.
5. A 20 ms grid gives proportionally more columns than a 40 ms one.
6. A column starts where the arithmetic says.
7. The grid covers the whole recording, including a duration just over a whole second.
8. A length of time is not an instant, which is the two-functions decision above.
9. An impossible frame length is refused: zero, negative, infinity, not-a-number.
10. A negative time is refused by every function that takes one.

Nothing was deleted.

**How they were run.** The whole backend was copied into a Linux container with the project's
dependencies installed, and `pytest` was run there, because this session's virtual machine cannot
use the macOS virtual environment. The full suite passes with the same two pre-existing failures as
before this task. `black --line-length 100` and `flake8` are clean on every file touched. Please run
`make lint` and `pytest` on the Mac to confirm.
