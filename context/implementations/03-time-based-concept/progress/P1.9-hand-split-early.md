# P1.9 and P1.10 — the split moves here, and a piece is always two hands

Tasks: P1.9 and P1.10 `[AITU]`. Decisions implemented: D-31, contract §2 and §5.
Date: 2026-08-06. Status: done. Resolves issues I-02 and I-05.

## 1. Why the split moved forward

Everything downstream measures one hand at a time. The gaps between a right-hand run and a held
left-hand chord are not a rhythm, and if they are left in the plot they bury the peak the user is
meant to name. So the hands have to exist before anything is measured, and the split cannot sit in
Phase 4 as originally planned.

The supervisor's instruction was to keep the whole thing simple and readable: raw onsets, impose the
granularity, split the hands, measure the peaks, attach a figure to each duration in milliseconds.
The new module is written to read exactly like that.

## 3. Decisions taken inside the task

**The unsplit matrix is kept on the result but never stored or sent.** It is useful for diagnostics
and it is what the split-loses-no-note test compares against. It has no place in the saved format,
which is why there is no `raw` step any more.

**A one-hand piece is not a different shape.** It is two hands with one of them empty, plus
`hideLeftHand` or `hideRightHand` in the layout hints. Detecting which is one line, and every
consumer, every stored file and every test then stays on one code path.

**`layout_hints_for` takes frame counts, not durations.** The defaults, 25 and 100, are one second
and four seconds at 40 ms. A piece at 20 ms should halve them to keep the dashed lines in the same
place on the clock, and the docstring says so rather than the function guessing.

**Nothing was changed in `hands/`.** The splitter reads `matrix.time_step_seconds`, which a time
matrix answers correctly, so it works on a wall-clock grid without modification. The one thing that
still reads `granularity` is the persisted assignment block, which carries a placeholder for now and
leaves in P4.4.

## 4. Things I believed that turned out false

I expected the hand splitter to need work before it could run on a 40 ms grid, because it was tuned
on a much finer one. It runs unmodified: it asks the matrix how long a column is and takes onset
groups, and both still make sense. The quality question stays open, and P4.3 is now the task that
records how it copes at 20 ms against 40 ms on the same piece. The supervisor has accepted that cost.

## 5. Tests

`aitu-backend/tests/test_time_pipeline.py`, eleven tests, all passing:

1. The pipeline gives two hands, both wall clock, both the same length.
2. The split loses no note: the two hands recombine into exactly what was played.
3. A held low chord stays on the left under a running melody.
4. **Changing the frame length changes the grid and nothing else.** At 20 ms there are twice as many
   columns, the same notes are placed, and an onset at 200 ms is column 5 at 40 ms and column 10 at
   20 ms: the same instant.
5. An odd frame length, 30 ms, works just as well.
6. Running twice gives the same answer.
7. A piece is always sent as two hands, with `matrixProcessingStep` fixed at `two-hands`.
8. A right-hand-only piece has an empty left matrix of the same length and `hideLeftHand` set.
9. A left-hand-only piece hides the other staff.
10. The result describes itself in a sentence.
11. An impossible frame length is refused before any work happens.

The whole suite still passes with the same two pre-existing failures.
