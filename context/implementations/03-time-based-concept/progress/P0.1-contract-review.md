# P0.1 — Review of the PRD, the decisions and the contract

Task: P0.1 `[AITU]`. Decisions reviewed: all of D-01 … D-31.
Date: 2026-08-06. Status: **blocked on the supervisor's answers to I-01, I-02 and I-03.**

## 1. What this task is for

Phases 1 to 4 and Phases 5 to 6 are meant to run at the same time, in two repositories that never
import from each other. The only thing that keeps them from diverging is the written contract. A
disagreement found later costs both sides; a disagreement found now costs one paragraph. This task
is the last point where the three documents can still be changed cheaply.

## 2. What was read

`PRD.md`, `decisions.md`, `contract.md`, `plan.md` and `checklist.md`, each against the other two,
and all of them against the code they describe: `schemas/matrix.py`, `schemas/score.py`,
`schemas/naming.py` and `vexflow-v2/src/matrix/types.ts`.

## 3. Result

The three documents agree with each other on everything the plan actually builds. The figure
vocabulary, the proportional comparison, the passage model, the ownership table in `contract.md` §6
and the phase order in `plan.md` are consistent, and the success criteria in `PRD.md` §5 each have a
task that produces them.

Three points cannot be implemented as written. They are recorded in
[`issues.md`](issues.md) as I-01, I-02 and I-03, and each one names the alternative I believe is
right. None of them blocks P0.2, P0.3 or P0.4, because those three tasks only add types that nothing
reads yet. Two of them block Phase 1.

- **I-01 blocks P1.3.** D-06 caps the stored sustain at one redonda of the active ladder, and P1.3
  writes that sustain while building the matrix. No ladder exists at that moment: the user names one
  after seeing the peak plot, which is computed from the finished matrix. A piece can also carry
  several ladders, one per passage, so "one redonda" is not one number for the whole matrix. The
  cheapest repair keeps the full measured sustain in the matrix and applies the cap in Phase 3, where
  the passage and its ladder are known. That also matches D-03, which says the matrix is a derived
  view and the raw timestamps are the record.

- **I-02 blocks P1.3 and P4.4.** `contract.md` §2 makes `rMatrix` and `lMatrix` required and allows
  `matrixProcessingStep: 'raw'`. D-31 puts the hand split after the matrix is built, so a `raw`
  matrix is a whole keyboard with no hands yet and has nothing to put in either field. Either the
  envelope needs an optional single-hand `matrix` field for that step, or `raw` should leave the 2.0
  envelope and the pre-split matrix should stay in an internal model.

- **I-03 is a clarification rather than a fault, and it changes what P5.1 has to build.**
  `LayoutHints.alignWindowMs` asks the renderer to give one x to onsets within 20 ms, but the payload
  gives the renderer only `startFrame`, an integer of 40 ms steps, so it cannot tell 15 ms apart from
  35 ms apart. My reading is that nothing is missing: D-04 groups onsets within 20 ms on raw times
  before the hand split, so those onsets already share a frame and a `groupId`, and sharing an x
  follows from sharing a frame. If that reading is right, `alignWindowMs` is information for the UI
  and P5.1 must be told that the alignment is inherited from the backend rather than recomputed. If
  the grouping in P1.2 turns out to run per hand rather than across both, then `PrintedNote` needs
  the raw onset time in milliseconds and the contract has to change before Phase 5 starts.

## 4. Smaller points, recorded but not blocking

**Python rounds halves to even.** D-02 defines the column as `round(onset_ms / frameMs)`. Python's
built-in `round` sends a value exactly halfway between two columns to the even one, which is
deterministic and therefore satisfies success criterion 3, but it is not the same answer as
`floor(x + 0.5)`. P1.1 should state which one it uses so a later reader does not treat a difference
of one column as a defect.

**`timeStepSeconds` is described twice.** `contract.md` §1 keeps it as a derived convenience, and §2
leaves it out of the interface. P0.2 implemented it as a computed property and not a stored field,
which satisfies both readings. If it should travel on the wire, say so and both mirrors change.

**`silenceGroupPx` is a pixel value produced by the backend**, while §6 gives the whole `time → x`
map to the renderer. It is a hint rather than a position, so it does not break the ownership rule,
but it is the one field in the payload measured in pixels.

## 5. Things I believed that turned out false

I expected the new `FigureName` to be the existing `Granularity` enum with two dotted entries added,
and planned to extend it. It cannot be: `Granularity` names the resolution of a column, and
`contract.md` §1 removes that concept from the grid entirely, while `FigureName` names a printed
glyph. They are two vocabularies that happen to share seven words. P0.2 therefore defines a separate
enum and leaves `Granularity` untouched until P4.4 removes it from the storage layer.

I also expected `contract.md` to be silent about `raw` matrices, since the renderer never sees one.
It is not silent: it lists `raw` as a valid processing step, which is what makes I-02 a real gap
rather than an omission.
