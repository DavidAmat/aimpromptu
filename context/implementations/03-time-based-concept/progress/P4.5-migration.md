# P4.5 — the migration, and the pieces it refuses to guess about

Task: P4.5 `[AITU]`, and P7.6 with it. Decisions implemented: D-01, D-03; PRD §5 criterion 5.
Date: 2026-08-07. Status: done, checked on screen.

## 1. Why this task looks smaller than it was planned to be

The plan describes P4.5 as re-deriving every stored artifact at 40 ms. That step no longer exists.
P4.2 made the wall-clock path read `events.json` and work everything else out on each request, so a
piece with its recorded notes intact is already on the new model. There is nothing to convert.

What there is instead is a disposal problem and an honesty problem, and the second one is the reason
the task matters.

The disposal problem: each piece still had seven files from the old pipeline sitting beside its
recorded notes, and they were built at a tempo that is written down nowhere. Section 4.1 of the P4.1
report shows that tempo had to be *recovered by trial* to read the grid at all. A file like that
looks authoritative and cannot be interpreted, which is the worst combination.

The honesty problem is success criterion 5: **every stored artifact either migrates or is explicitly
marked as needing re-derivation, and nothing is silently reinterpreted.** A piece transcribed before
the note times were kept has a grid and no way to rebuild it. Reading that grid as wall clock would
move every note in it and say nothing. So it has to be refused, in words, on the screen where the
person looks.

## 2. What a person sees

Nothing changes for a piece that is fine. *Mr Blue Sky* opens in **Rhythm** exactly as before.

A piece the migration could not carry over now says so twice:

- In the **Audio library** list on Upload / Input, its row carries a warning triangle and, under the
  name, the sentence "This piece was transcribed before the recorded note times were kept, so there
  is nothing to write a sheet from. Open Upload / Input, pick it, and press Run transcription."
- On the **Rhythm** tab, the same sentence appears as a warning at the top instead of the plot, and
  the plot stops waiting rather than turning a spinner at somebody whose piece will never load.

Transcribing the piece is what fixes it, and doing so clears the mark.

## 4. How the script works, and what it refuses to do

Run it with `uv run python scripts/migrate_to_time_matrix.py`. **A dry run is the default.** It
prints one line per artifact saying what it would do and changes nothing; `--apply` performs it.

Applying copies the whole `data/` tree aside first, to `data-before-time-migration/`. That is not a
formality: P4.1 established that `data/audio/**` is gitignored, so the recorded notes exist in one
place only, and every later step is irreversible without the copy. A second run makes a second copy
rather than overwriting the first.

Then, per artifact:

| Situation | What happens |
|---|---|
| has `events.json` | its old grids move into `_replaced-by-time-matrix/` beside it |
| has `events.json` and a stale mark | the mark is removed |
| no `events.json` | marked, and **every old file is left exactly where it is** |
| a saved version on a beat grid | marked; nothing is touched |

**Nothing is deleted.** The old files are moved, not removed, because this is the one operation
nobody can undo and disk costs nothing.

## 5. Decisions taken inside the task

**The mark is a file next to the piece, not a field in its metadata.** `metadata.json` describes the
audio, and whether a transcription can be drawn is a fact about the `matrices/` folder. Keeping them
apart means renaming a piece cannot disturb the mark, and deleting the folder clears it by
construction.

**The mark carries the sentence, not a code.** The same text reaches the library row and the Rhythm
warning without either screen composing its own wording, so the two can never disagree about what is
wrong. It costs a longer file and removes a class of bug.

**`hasNotes` and `needsRederivation` are computed per request, not stored.** A list of pieces has to
say which of them can be drawn, and asking per row would be one request per piece. A stored flag
would be one more thing that can fall out of step with the folder it describes.

**The 409 from `/time/{uuid}/score` was rewritten.** It used to read "Re-transcribe it
(POST /matrix/transcribe)". That string reaches the screen unchanged, and it is an instruction
nobody reading the app can follow. There is now a test asserting the answer contains no endpoint.

**The backup folder is named after the source, not the clock.** Reading the time would make two runs
of the same script disagree, and the same rule already applies to the workflow scripts in this repo.

## 6. Things I believed that turned out false

I believed the migration would be the risky part of Phase 4, because the plan says so and because
"nothing here is reversible without the raw events" is written at the top of it. On this tree it
moved seven files and marked nothing. The risk was real when the plan was written and P4.1 measured
it away; what was actually dangerous was P4.2, which deleted the code five working screens depended
on.

I also believed that flagging a piece was enough to satisfy criterion 5. It is not, on its own: a
flag nobody sees is the same as silence. Half of this task is the two places the sentence appears,
and the reason the Rhythm warning matters more than the library row is that a piece can be selected
before it is understood to be broken.

## 9. What is left, and one thing to decide

I did not run `--apply` against your `data/` folder. Two reasons. The seven files it moves are the
only remaining evidence of what the old pipeline produced for that recording, and P4.3 may want to
compare the old hand split against the new one on the same piece. And it is your data: a dry run is
what a worker should leave behind.

To run it: `uv run python scripts/migrate_to_time_matrix.py` in `aitu-backend` reads out what it
would do, and the same command with `--apply` does it. It copies `data/` aside first either way.

P4.3 inherits an unmigrated tree on purpose, which is the state it wants for the comparison.

P4.4 is unaffected: the marker file is keyed by the audio uuid, which the new version-folder scheme
does not touch.
