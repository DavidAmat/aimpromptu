# P7.10 — the reading is saved with the piece

Task: P7.10 `[AITU]`. Decisions implemented: D-09, D-17, D-19, D-34.
Date: 2026-08-08. Status: done, checked on screen.

## 1. Why this was needed

Phase 4 made the backend store one file per piece, `events.json`, and work everything else out on
each request. That is right for the parts that are derived: the columns come from the recorded
notes, the figures from the ladder, the beams from the figures. Losing them costs a second of
arithmetic.

But four things on the Rhythm screen are not derived from anything, because nothing in a recording
implies them:

- which pile of gaps is the beat, and what it is called (D-09)
- where the piece changes speed, and what a gap is worth after each change (D-19)
- the notes drawn as a different figure by hand (D-17)
- the notes the reader asked to start a new beam (D-34)

All four lived in the tab's own state and went when the tab did. A reader who came back to a piece
started again from the plot, and the work they lost was the only work in the screen that was theirs.

## 2. What a person can now do

Name a gap, make whatever changes they want, and press **Save this rhythm with the piece**. Coming
back to that piece restores the reading: the same hand, the same anchor, the same speed changes, the
same renamed notes and the same beam breaks.

Under the button the screen says which it is: *Nothing saved yet, so this reading goes when you leave
the tab*, or *Last saved as Negra (quarter) = 337 ms.*

## 3. What it stores, and where

`data/audio/<uuid>/matrices/rhythm.json`, beside `events.json`. About two hundred bytes for a piece
with no hand edits.

```json
{
  "schemaVersion": "1.0",
  "hand": "right",
  "frameMs": 40.0,
  "anchorFigure": "negra",
  "anchorMs": 337.3,
  "speedChanges": [],
  "overrides": [],
  "beamBreaks": [],
  "savedAt": "2026-08-08T10:25:19Z"
}
```

**The frame length is part of it**, and it is the field most likely to be wondered about later. A
saved reading is a set of column numbers, and the same numbers mean different moments at 20 ms than
at 40. Storing the length they were written at is what lets a future reader of this file know
whether the numbers still refer to what they referred to.

**The hand is part of it** for a smaller reason: it is not on the sheet, but it is what the reader
was looking at, and returning them to the other hand's plot would be a small surprise every time.

## 4. Decisions taken inside the task

**One reading per piece, replaced rather than versioned.** A rhythm is a decision, not a state worth
a history: what a reader wants back is the last reading they were happy with, not a list of the ones
they abandoned. Saving twice overwrites, and there is one file.

**Transcribing again throws it away.** The columns in a saved reading describe the notes that were
there before. A new transcription is a different set of notes, so the numbers would point at music
nobody chose, and a reading that is quietly about something else is worse than no reading at all.
`transcribe_audio` clears it, next to where it writes the new events.

**A file it cannot read counts as nothing saved.** An older shape, or a truncated write, comes back
as `None` rather than raising. Losing a reading is a nuisance and the reader can name the gap again;
refusing to open the piece over it would be worse.

**Saving is a button, not automatic.** Every other change on this screen is instant and reversible,
so an autosave would be defensible. It was refused because the reader is still trying names: writing
each attempt to disk would make the stored reading the last thing they tried rather than the one
they chose, which is the opposite of the point.

**An override is stored with `row: 0`.** The screen keys overrides by `hand:startFrame` because an
override belongs to a chord rather than to one notehead — two notes struck together are one event,
and giving one of them a different figure would print a chord that disagrees with itself. The
contract's `FigureOverride` carries a row, so a placeholder goes in it. That is a small dishonesty in
the stored shape and it is written down here rather than hidden: if per-notehead overrides ever
become real, this field is where the difference will show.

## 5. Things I believed that turned out false

I expected to have to keep the saved reading and the live screen in step, and to show the reader when
they had drifted apart. That is not worth building: the screen restores the reading on arrival and
saves on request, and between those two moments the only honest thing to say is what the last save
was, which is one line of text. Anything more would be tracking a diff nobody asked for.

`tests/test_saved_rhythm.py`, nine tests: the round trip keeps every field; a piece with no reading
says so rather than inventing one; saving twice replaces and leaves one file; a reading can be
forgotten; an unknown audio is a 404 on both verbs; a piece that was never transcribed is refused

clean.

## 8. Checked on screen

Named the 337 ms pile a negra on the real recording, wrote the sheet, pressed **Save this rhythm with
the piece**. `rhythm.json` appeared beside `events.json` holding `negra` at 337.3 ms and 40 ms
columns. Reloading the page and writing the sheet again showed *Last saved as Negra (quarter) =
337 ms.* No console errors.

**What to check yourself.** Open **Rhythm** with *MR BLUE*, name the 337 ms gap, write the sheet,
rename one note by clicking it, then press **Save this rhythm with the piece**. Reload the browser
and open the tab again: the anchor and the renamed note should both be back, and the line under the
button should say when it was last saved.

## 9. What is left

The reading is saved per **audio**, not per named piece in a library. When the Library stops being a
placeholder, a track will want to carry its rhythm the same way, and this file is the shape to move
rather than a second mechanism to invent.
