# P1.4 — `PianoMatrix` carries a frame length

Task: P1.4 `[AITU]`. Decisions implemented: D-01, D-30.
Date: 2026-08-06. Status: done, additively; see I-04.

## 1. Why the model had to change

`PianoMatrix.time_step_seconds` was `beats_per_column * 60 / tempo_bpm`. Every module that asks a
matrix how long a column is was therefore asking a question whose answer depended on a tempo. A
wall-clock matrix has no tempo, so the model needs a second way to answer.

## 2. Files

Changed:

- `aitu-backend/src/aitu_backend/matrix/model.py`

## 3. What it does now

`PianoMatrix` has a new optional field, `frame_ms`. When it is set the matrix is a **time matrix**:

- `time_step_seconds` is `frame_ms / 1000` and no tempo takes part.
- `beats_per_column` **raises**, with a message saying a frame is milliseconds of wall clock and not
  a note figure.
- `is_time_based` is true.
- `repr` prints `40 ms/frame` instead of `semifusa, 178 BPM`.

When it is absent the matrix behaves exactly as it did before, so every existing module, the storage
layer and the editing operations keep working. `copy`, `with_grid` and equality all carry the field.

Build one with `PianoMatrix.time_based(grid, frame_ms=40)`. The 1.x `granularity` and `tempo_bpm`
fields still exist and hold placeholders, because `hands/`, `ops.py` and `storage/` read them and
they only leave in Phase 4.

## 4. Decisions taken inside the task

**`beats_per_column` raises rather than returning zero or `None`.** This is the guard that stops a
beat value leaking back into the layout through a module written before the refactor. A quiet zero
would produce a page of notes stacked on one x with no error anywhere.

**A separate constructor rather than new default values.** Giving `granularity` and `tempo_bpm`
defaults would let a 1.x caller forget them and get 60 BPM silently. `PianoMatrix.time_based` fills
the placeholders itself, so no existing signature changed and no existing call site can drift.

**`to_envelope` was not touched.** It still produces the 1.x `PianoMatrixEnvelope`, which needs a
tempo and a granularity. The 2.0 envelope is built in Phase 3, and I-02 has to be answered first
because the contract has no shape for a single-hand `raw` matrix.

## 5. Things I believed that turned out false

I expected the plan's wording, "carries `frame_ms`, not granularity + BPM", to be a small edit. The
two fields are read by the hand splitter, the granularity collapse, the isochrony pass, the tempo
map, the text notation format, the storage paths and four API routers. Removing them is Phase 4's
work, not this task's, and attempting it here would have broken the running app for three phases.
What this task can honestly deliver is a matrix that *can* be wall clock, which is what P1.3 needs.

## 6. Tests

No test file of its own. The behaviour is covered where it is used, in
`tests/test_time_matrix_build.py`: `test_the_matrix_is_wall_clock_and_has_no_beat_value` asserts
`is_time_based`, the frame length, the derived seconds per column, and that `beats_per_column`
raises.

The whole existing suite passes unchanged, with the same two pre-existing failures, which is the
evidence that the addition is backwards compatible. Run as described in `P1.1-time-grid.md` §5.
