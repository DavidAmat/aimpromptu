## 1. What now works

An audio goes in and a full score payload comes out, over HTTP, with no tempo anywhere in the path.
The three routes are the three things the user does:

| Route | The question it answers |
|---|---|
| `GET /time/{uuid}/peaks` | where does the rhythm actually pile up? |
| `POST /time/{uuid}/ladder-preview` | if I call this peak a negra, what does everything else become? |
| `GET /time/{uuid}/score` | draw it |

They live under `/time` while the 1.x `/matrix` routes keep the running app alive. P4.2 folds them
together.

Nothing is cached and nothing is written. Every request re-derives from the stored `events.json`,
which is what makes `frameMs` a query parameter instead of a migration. On a five-minute piece that
costs a second or two and buys a system with no stale state.

## 3. Decisions taken inside the task

**The raw attack time of every column is carried forward.** This is the most consequential choice
here. After the snap, the only gap available downstream would be a whole number of frames, so a
211 ms gap would arrive as 200 and a 125 ms one as 120. Both are close enough to change a figure.
The build report therefore keeps a `column -> raw seconds` map, and the printed length is measured
between those values. The snap decides where a note sits; it never decides how long it is.

That map is also how the peaks endpoint measures per hand without any lookup. The hands are split
after the snap, so a hand's attacks are its onset columns, and each column's real time is one
dictionary access away. Issue I-05 is closed by construction rather than by a workaround.

**`nearest_figure` was not rewritten.** P3.2 imports it from `matrix/ladder.py` under the name
`select_figure`. Two implementations of the proportional comparison that disagree would put a
different figure on the page from the one the peak preview promised.

**`both` measures each hand separately and adds the two sets of gaps together.** It does not measure
the merged stream. A gap between a right-hand run and a held left-hand chord is not a rhythm, and
letting it in buries the peak the user is meant to name.

**The last note of a hand runs to the end of the piece**, capped at a redonda like any other. It has
no next onset, so the alternative would be to use its own release, which contradicts D-14 for that
one note only.

**A column with no recorded time falls back to its middle.** That happens for a matrix loaded from
disk rather than built in this run. Half a frame is the least wrong guess available and it is
documented where it happens.

**Passages carry more than the plan asked for.** `split_passage` and `with_ladder` exist because the
frontend in P7.2 and P7.3 needs to draw a boundary and change one ladder, and both operations have
to keep the tiling intact. They are small and fully tested.

## 4. Things I believed that turned out false

I expected the figure to be chosen from the gap in frames. It cannot be, for the reason in §3: at
40 ms columns the swing pair 211/125 becomes 200/120, and 120 is close enough to the boundary
between a corchea and a semicorchea that the answer starts depending on the grid. The whole point of
the refactor is that the grid decides nothing about the figure, so the raw times had to be carried
through. This is worth knowing for anyone tempted to simplify `printed_notes_of_hand`.

I also expected the hand split to make the 00:46 case harder, because this pipeline splits on a
40 ms grid rather than the fine one the original measurement used. It does not: F5, E5 and C5 all
land on the right hand and all three print as corcheas.

## 5. Tests

`tests/test_time_score_payload.py`, eighteen tests, and `tests/test_time_score_api.py`, thirteen
tests. All pass. The ones that carry weight:

- **`test_the_worked_example_at_00_46_prints_three_equal_corcheas`** — success criterion 1, on the
  real recording. The three notes were played 120, 217 and 122 ms apart and all three print as
  corcheas.
- `test_changing_one_passage_ladder_moves_nothing_outside_it` — D-21, checked by comparing every
  note before and after, not by inspection.
- `test_a_figure_shift_renames_a_passage_without_moving_a_note` — D-18.
- `test_the_gap_is_measured_between_the_real_times_not_between_columns` — the §3 decision.
- `test_no_note_is_ever_printed_longer_than_a_redonda` — D-06 and D-15, the cap that moved here.
- `test_a_held_note_under_a_run_stays_long_on_the_other_hand` — success criterion 6.
- `test_the_frame_length_does_not_change_which_figures_are_printed` and
  `test_a_finer_grid_moves_the_columns_but_not_the_figures` — the granularity is a layout parameter.
- `test_both_halves_of_the_shuffle_print_as_corcheas` — the same result over HTTP.

Nothing was deleted. The whole suite passes with the same two pre-existing failures.

## 6. What is left open

**P3.6 is half done.** Overrides are stored, carried in the payload and proved not to change any
other note. Applying one to a glyph is the renderer's job in P6.1, so the task cannot close here.

part of P7.2, where the user draws one.
