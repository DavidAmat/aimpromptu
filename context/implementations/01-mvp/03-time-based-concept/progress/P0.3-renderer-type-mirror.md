## 1. Why the renderer gets the types before it can use them

Phase 5 may start as soon as Phase 0 lands, and it will be written against a payload the backend
cannot produce yet. Declaring the payload's shape now is what makes that possible. Nothing in the
package reads these types today; they are there so the renderer work can be typed against the same
names the backend emits.

## 3. Decisions taken inside the task

**The new types are not re-exported from `src/index.ts`.** This is the one thing in this task worth
reading carefully. The package already exports a `FigureName` from `notation/figure-selection.ts`,
with the 1.x English names (`quarter`, `dottedEighth` and so on). The contract's `FigureName` is the
Spanish closed vocabulary. Two exports of one name do not compile, and `tsc` says exactly that:
`error TS2300: Duplicate identifier 'FigureName'`.

Renaming either one would put a name in the public surface that does not appear in `contract.md`,
which is the one thing this phase exists to prevent. So the new types stay module-level for now.
Phase 5 and Phase 6 import them from `./matrix/types` directly, which is all they need. P6.1 rewrites
`notation/figure-selection.ts` and deletes the old `FigureName` with it; **the public re-export of
the 2.0 types belongs to that task**, and it is a two-line change once the collision is gone.

## 4. Things I believed that turned out false

I believed adding types to `types.ts` and exporting them from `index.ts` was one mechanical step,
and made both changes in one go. The `FigureName` collision above showed that the export half is not
mechanical at all, and the export was reverted. The lesson for P6.1 is that the old figure
vocabulary is still load-bearing in the public surface, not only inside the drawing code.

machine. The change is type declarations only, so a test failure caused by it is very unlikely, but
it has not been proven. Please run `npm run check` in `vexflow-v2` on the Mac before Phase 5 starts.
