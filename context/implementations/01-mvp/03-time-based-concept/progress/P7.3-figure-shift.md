# P7.3 — writing the same playing one step longer or shorter

Task: P7.3 `[AITU]`. Decisions implemented: D-18, and a correction to the code that implements it.
Date: 2026-08-08. Status: done, checked on screen.

## 1. Why this was needed

Naming a gap fixes every figure in the piece by proportion, and the name that fits the data is not
always the name that reads best. *Mr Blue Sky*'s 337 ms pile is the beat, and calling it a negra
gives a page of corcheas and semicorcheas. Calling it a blanca gives the same music in negras and
corcheas. Neither is more correct: the recording is unchanged and so is every position on the page,
because a column is wall clock and the name of a note has no say in where it sits.

Until now the only way to try the other reading was to re-pick the anchor figure from a dropdown and
work out for yourself which one was one step away. `shift_ladder` existed in the backend, tested,
with no way for a reader to reach it.

## 2. What a person can now do

On the Rhythm tab, under the name, there are two buttons: **Write it one step longer** and **Write
it one step shorter**. Pressing one moves the anchor along the ladder, and pressing **Write the
sheet** redraws with every note renamed.

Checked on the real recording: `negra = 337 ms · ≈178 BPM` becomes `blanca = 337 ms · ≈356 BPM`, and
the peak plot relabels every pile with it — 67 ms goes from semicorchea to corchea, 120 from corchea
to negra, 674 from blanca to redonda. The sheet redraws with open noteheads where it had filled
ones.

## 3. The correction: a step is a doubling

**This changes behaviour that P3.5 shipped and its test pinned, so it is set out in full.**

`shift_ladder` sorted the whole vocabulary by length and stepped along it, which put the dotted
figures between the plain ones. One step longer from a negra landed on a **dotted** negra, and two
steps landed on a blanca.

D-18 says the opposite, in its own words: "`negra = 300` becomes `blanca = 300`, and everything below
shifts with it." The function's own docstring said the same thing twice over, with its example of a
passage written in semicorcheas becoming one written in corcheas. Only the code and its test
disagreed, and they disagreed with each other's stated intent as well as with the decision.

The reason the decision is right, beyond being the decision: a dot is an exception the vocabulary
allows on two figures so that one held note can be written (D-12). It is not a rung. Stepping onto
it re-scales the whole ladder by 1.5 rather than doubling it, which is not what "one step longer"
means to anyone reading music, and it produces a ladder on which no ordinary run of notes lands
cleanly.

So `SHIFT_LADDER` is now the seven plain figures, semifusa through redonda, each twice the one below
it. A dotted anchor, which a reader cannot currently set but the type allows, steps from the figure
it decorates.

This is recorded here rather than in `issues.md` because no decision was found wrong. The decision
was right and the code did not implement it.

## 4. What is not done: shifting one passage rather than all of them

D-18 and the plan both speak of shifting **a passage**. This shifts the piece.

The reason is the wire format rather than the idea. `GET /time/{uuid}/score` takes one
`anchorFigure` and a list of `boundaryMs`, so every passage is built with the same figure and a
different millisecond value. Per-passage figures need a `boundaryFigures` parameter beside
`boundaryMs`, and a control per passage in the UI to go with it.

For a piece with no speed changes, which is the common case and the only case on this machine, the
piece is exactly one passage and this task is complete as written. For a piece with speed changes,
the buttons shift all of them together. The UI says so.

## 5. Things I believed that turned out false

I expected to call `shift_ladder` from the frontend. There is nothing to call: a shift is the same
`anchorMs` under a different `anchorFigure`, so it is one piece of state changing and the existing
request carries it. What the backend function is for is the passage-level operation in section 4,
which is still unbuilt on the wire.

I expected the note positions to be identical before and after, and said so in an earlier draft of
this report. They are not, and D-33 says why: a beamed run is set tighter than the same notes
unbeamed, so renaming a run of corcheas to blancas removes the beams and widens the passage. The
systems then break in different places. **D-21 and success criterion 2 still hold** — nothing
outside a renamed passage moves — but "renaming moves nothing at all" has not been true since
beaming landed, and this is the first screen where a reader can watch it happen.

## 8. Checked on screen

Read off the page: pressing **Write it one step longer** and then **Write the sheet** turns the
header from `negra = 337 ms · ≈178 BPM` into `blanca = 337 ms · ≈356 BPM`, relabels all eight piles
in the plot, and redraws the staff in longer figures. No console errors.

**What to check yourself.** Load *MR BLUE*, open **Rhythm**, name the 337 ms gap a negra and write
the sheet. Then press **Write it one step longer** and write it again: the same music should appear
in longer note values, and the header should read `blanca = 337 ms`. Press **one step shorter**
twice to get back past where you started, to `corchea = 337 ms`, which is the reading that gives a
page of very short notes. Nothing about the recording changes in any of them.
