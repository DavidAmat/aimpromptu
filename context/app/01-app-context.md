# AImpromptus

This is a web app that we pretend to build to catalog existing songs and create their corresponding piano versions.

The idea of this project is first to serve a personal need, which most likely will imply the project being run locally on my own computer, using my GPU, and being accessible within my local network. That will be kind of the first iteration
Then, if this gets enough traction, we are going to consider the production-based solution for this. There are some features that we are going to not include because they are not legal, but we are going keep in mind that this project can be, at some point, ported into something that can be ready for production.
This is also one of the reasons why we decided to containerize the backend and the frontend: we think that at some point this can become a web app hosted in any cloud provider. So far, we are going to assume that we are running them locally until we reac hthe "production-based" solution.

## Glossary

- **Piano Matrix Notation**: read `context/backend/piano-matrix-notation.md`. Basically, this is the disruptive idea of the web app. We are going to change the way that we render piano sheets and that music is rendered. We are going to propose a new notation that is more lightweight to port, and it also contains some freedom to add new metadata to a kind of UI that we have enabled to both visualize, edit, or create from scratch any kind of new piano sheet that we want. Whenever we say this notation, we refer to a matrix that contains, on the rows, the different piano keys and, on the columns, different time frames, so that we don't use at all any piano notation for measures, bars, etc... Our measurement is time and the keys (onsets, releases and sustains). Whenever we refer to this notation, we don't refer to the audio file or any other metadata that comes from the piano sheet edition, we simply refer to the matrix itself (sometimes the matrix is in a sparse notation (recommended) or a full notation (with lots of 0's)). We will refer to this format as `.pmn` ( P= Piano, M = Matrix, N = Notation)
- **Metadata**: Whenever we are editing a given piano sheet, we are maybe editing some metadata like adding, for example, the lyrics, changing the overall key signature of the song, or changing the key signature of a given passage, we add notes fingering, we add ottava annotations, we can decide if a figure it is shown as a "negra", "blanca", etc... anything that you can visualize in the piano sheet that is not about pure 0's, 1's or -1's of the piano matrix notation format. Also, in metadata, we can have the user ID of whoever created this project.
- **Audio**: Some songs will have an attached audio file, so that our editor allows us to have the original audio, some modified audio, a composition of several audios that we recorded, a composition of audios that we just gathered together in order to play the given song with audio. We are not going to create some sound out of the .pmn notation, but we will rely on pure audio files that will be **aligned** temporarily so that whenever the cursor of the player of the piano sheet notation is in a given time frame, the audio file is perfectly aligned on that time frame to sound that same moment of the audio too. 
- **Project**: A given project is the bundle of an audio file plus the piano matrix notation plus the metadata. Sometimes, for a given song, we can create different projects because, for the same song, we can have the same piece played by different levels of difficulty or different kinds of versions. If you want to make something softer or more acoustic, or something brighter, we give this the capability to name a "project" to be a kind of a "children" of a given song. We will have, inside a song, different ways to have different versions of that song, and every version will be attributed to its own user who created it in the metadata of that project. Such files that belong to the project can be bundled into a given download artifact, which is very flexible and portable so that anyone can then reuse those artifacts and have them uploaded back again into this web app (so that they are rendered the same way and they are displayed the same way). It has portability and standardization, and it's very lightweight, so that whenever we refer to an export or import of the files that belong to a project, we refer to the artifacts of a project.
- **Music Library**: The music library is basically an ontology that is derived from web scraping the internet about all the music history, artists, songs, albums, and any other metadata that we can incorporate into it. We also can have different levels of regions so that maybe we filter for songs that are worldwide, or Spanish, or Catalan, etc... It is totally independent from the project. The projects have to attach to a given song of this music library. We will try to make some kind of deduplication so that the same song doesn't appear twice in the catalog and it is univocally within a given artist or set of artists that may contribute to it. All the music entities of this library should have their own ID so that even if two songs have the same name (i.e "Heaven" is a song from "Bryan Adams" but also "Avicii") they are different entities because they have different ID and different metadata and artists / albums associations.  There is one thing that we would allow: that a given artist ID, for example, can have multiple associated artist names (for example in some songs we may have "Jackson Five" or "The Jackson 5", etc...) This can potentially create some duplicity, so we are going to allow converging all of these different names into the same ID. There will be a default one that we put in this kind of artist table, but we're going to allow having different ones, so it is okay if you create an artist ID and then an artist name ID so that it can happen that one song is referenced by its artist name ID, but underlying this artist name ID is the artist ID. Whenever we want to convert things into the same umbrella of the same artist, we use the artist ID and not the artist name ID. There is an important distinction here in the music library: we will have two kinds of databases for the library: we will have a private one so that every user will have their own private library, so they can put all the songs, playlists, etc... And it won't be public. We will have the public library, which will be the one that will be shared with any person. It will also have the same entities, but it will be something separated so that any kind of person that wants to contribute to the public library needs to open a request, similar to how Git works, no? Imagine that every private library is a kind of feature branch, and in order to publish something into the public library, we need to open a request, so the master user needs to review it. The idea is that the platform provides the users with the capability to promote publicly their own libraries of songs or versions of songs, and so on, so that we are able to give credit to the creators of each song.  Each song will have different versions (see later explained section) so authors can contribute to the `Other versions` versions. 
- **Users**: We will have a master user that will be the one that will review revisions, or that will be the owner of all the public library that we will have. The rest of the users will have simply a user ID that will be numerical, and will have a username that will be the one that will be displayed for other users. In principle, any private library cannot be viewed by other users, but of course you can share your private library between users, so that will be allowed in your shared library tab. But if not, otherwise, the only way for a given user in the public library to be exposed is if it tries to publish a given song and it gets reviewed positively, so it gets approved. Then that username gets into that song metadata.

# Music Library

Whenever a project is finished, the user can decide either to save it into its personal vault, Or to associate it to any existing song that we have in our music library.
One song in our library can be pointed to by different projects, Maybe different versions of that song, or different users that created different versions, or different styles, or different difficulties of playing the same song made in different projects.

The music library is created independently and will have an existing ontology that we are going to create from scratch. We're also going to let the users, or the master user, expand it or do some refactorings of the existing one.
The idea is that we will start with some web scraping of some of the most well-known songs, artists, albums, and also the temporal ranges.
Every song will have its own metadata.
Songs will have versions, so that every version is a different project. We will have a default version that will always get rendered whenever we select a given song and we visualize the piano sheet, but we are also going to have a versions tab or dropdown in order to select different difficulties that exist or different Compositions that other users created, so that every user ID can have its own versions of that same song saved so that we can access them and sort them by popularity, etc... So yes, a project can be liked by other users.

There are different libraries and different ways to store projects, move projects around, etc...

This simulates a main branch in GitHub in which we will have all of the music library of Songs, Playlists, Artists, etc... Open for everyone in the public to access the different versions of a song, download them, and so on.
However, not everyone can publish things publicly, so the first step is always to publish something in the private library because every user will have their own private library. They will promote a given private song or a given private playlist to the public library via a request (a kind of PR that the master user will be able to review, we need indeed a Admin Panel for this user).
The thing is that we should understand the difference between projects and the songs, artists, and all this kind of music library that we call, which has a separate ontology from the project one. Then, whenever the user wants to promote this new song for a new artist into the public library in this pull request, the master user will see that there is also a request to create a new artist and a new song. ### Versions
Remember that songs are organized within versions, so that whenever a user requests to promote a given song, it should provide which version it wants to upload.
By default we are going to have the following **versions**:

- Hard: pointer pointing at the public project in the Public Library uploaded by a given user which was accepted by the master user to become the Hard version of that song.
- Medium: pointer pointing at the public project in the Public Library uploaded by a given user which was accepted by the master user to become the Medium version of that song.
- Easy: pointer pointing at the public project in the Public Library uploaded by a given user which was accepted by the master user to become the Easy version of that song.
- <New_version>: This is a capability that allows people to put names for the new versions. For example, if you want to make an acoustic version, it does not fall into any of the categories of hard, medium, and easy, which mostly reference the original song. Maybe this new version is kind of a version of the original song. This is why we are going to allow the flexibility here to put any new text the user wants. Of course, since this will be under revision, the master user will revisit what this will be (this new version name) and will either accept it or change it.
- **User versions** (i.e `user_versions/` folder):
    - <user_id> as a folder but use <user_name> for visualizations
        - <version_name>: (i.e easy, medium, hard, acoustic, etc... any of the versions that the user tagged this project for when it opened the PR). We will here follow some kind of simple rules about simple texting so that we don't allow very complex names or very weird characters in this versioning. We will be very strict about it otherwise creating freestyle names is a bit dangerous letting the users write what they want. This is why, for this kind of version name, we allow the user in the private library to put whatever name they want and also to rename it in the future. Whenever they open a PR, if we don't agree with that, we can suggest a renaming so that the user can adapt to the renames that are accepted.
            - <project_id>: The user, when it made the request to promote this project ID to the public library, selected which version it wants to go for: either the hard, the medium, or the easy or a new version (i.e "acoustic").
            - We are only going to let one project ID inside a given version name because we don't want any duplicity, so a given version will only have one project ID.
        - So here, version names can vary from song to song, no? This new version tag will not become a new general version for any kind of song. We are going to only allow this new version name for this song.

## Private Library
The difference between the public library and the private library is that the private library is only accessible by that user, and the private library starts from scratch. The public library will have all the content that has been published or promoted to public so far in this web app.

We will have this kind of flexibility to create its own private library, no? Every user can have its own private library and have everything organized there in songs and playlists, because it does not need to download everything that exists in the public library.

Whenever the user is in the private library, it has maximum flexibility to decide which kind of new version names it wants to create. That should be another way to open PRs.
- Rankings: In the web scraping that we are going to do, we will get the rankings of a given song at different temporal moments. We should have a proper way to identify what the highest ranking (the lowest number) a given song reached in order to infer a kind of popularity measurement. We should come up with a formula in which, if we have different temporal dates for a given song and we have the rankings, we can calculate a popularity score. And here, for popularity score, we don't want to do a mean of the rankings because we don't care if, when the song was unknown, it was ranked in place 2,000 or 3,000. What we care about is whenever the song is popular, whenever the song appears in the top 50 of the charts, or whenever it's in a very high position and keeps maintaining a very good number throughout the weeks. This is a very good sign, no? One of the very good signs is often to reach very low positions in a very short amount of time, so this is okay. Another good sign is that, even though the ranking is not very low, it's maintained for example at 10-30 position range during many weeks, this is also a good sign of popularity (maybe not that much of a song that reached top 10 for 1 week only maybe, but close in popularity). Here, expect to have the data in different kinds of formats, so that the underlying metadata for ranking is maybe a series of temporal snapshots and the position of the song for a limited range of time, of course. You have to come up with a new metric that we call popularity.
- Popularity: This is the metric that we will come up with by analyzing the rankings. We will collapse it into a number between 0 and 100, so the closer to 100, the higher the popularity of the song. For example, a song that has been a lot of times at ranking number 1 and has maintained it a lot of times throughout all of the times can be considered near 100. This will be a very good way to sort the songs within a given artist or sort the songs within a given decade, so that we are able to have a sorting logic by popularity thanks to this. It is also very important that this logic of computing the popularity takes into account the date range, no? For example, if we ask about the popularity overall, then we get this global score. If we ask about the popularity, maybe on the last 2 years, this changes a lot because we need to filter these rankings only on the last 2 years, no? Popularity is always referenced relative to a time period. If we want popularity in the 80s of a given song, we can calculate this relative to that date range. If we make it overall, which is the default value for the popularity, then we consider all the times. This is very important because if we filter by a given decade, and ask to sort by popularity, these popularities need to be recalculated on the fly by this filtered time range, so we should find a way that is flexible, easy to compute and fast and it is dependant on the time range.
- Region: Sometimes popularity is based on the region of the song, so there are some local hits that are only popular in a given country, in a given local region, or within a given country, or have a specific language. # Storage Layers

This is very important to understand because I have talked so far about the UI and all the capabilities and all the elements that we will have, but we haven't talked a lot about how we will store every piece of data underlying all of this.

As I see it, there are three storage layers.

## Layer 1: Personal Vault

Whenever a user starts a new project, starts a song from scratch or from a given source, downloads a YouTube video, or whatever, this stores some data into a private vault for that user. The data that is under this vault sometimes is temporal data, for example, whenever we download a YouTube video and we analyze the rectangles out of it, This is a temporal file because after we have created the notes out of this video, we're going to delete this video. This is an example of a temporal file. However, there are also examples of files that will not be temporal. For example, if we are under a given project and we are working on a given song, but we haven't yet published this song into the private library, we want to save it into this vault until we promote it into the private library. At the moment we promote it into the private library, we make a copy of these artifacts and we promote them to the private library storage layer, which ultimately makes the private vault for this project be deleted because it's not something that's a work in progress. It's something that's already consolidated. Once we work on a song in the private library and we want to change it or modify it, this opens a new file in the vault coming from this private library. It feels like a kind of staging mechanism so that whatever we have committed is already in the private library, as are all the artifacts. Whenever we want to edit something, we make a kind of feature branch in which we copy the artifacts. We put them into this private vault, where we allow making edits, changing things, and so on. They don't get propagated to the private library until we hit Save to or Promote to Private Library. At some point, we can have a copy of the same song: one that's consolidated in the private library and one that's a work in progress with some edits in the private vault. This offers a lot of flexibility for the users to modify songs without losing the progress or having a proper guarantee that, if they make a change they don't like, they always will have the original song that they already had in the private library without any change. Also, another example that I have come up with as a temporal file will be whenever we have an audio that we upload and then we trim it and cut it. We are producing a new cut audio, so the original audio can then be discarded. This is important because we don't want to keep the original audio after some cuts or edits for composition, and so on. The only option in which we are going to permit different audio files is whenever we are composing different audios that are joined sequentially. For example, imagine that I'm working on a given song and I want to re-record one of the sections or one of the passages. This creates two audio files so maybe the overall audio to play is:
- audio 1: from 00:00 to 01:23
- audio 2: from 01:23 till 01:32
- audio 1: from 01:32 till 03:34 (end) (so here, note that audio number 1: we discarded the audio that was from second 23 to second 32 in favour of the newly recorded audio 2). This is just an example.
See also how important it is that the metadata controls the timestamps of the audios and the relative paths of the audios. That way, whenever we copy-paste something, we can copy-paste the metadata of the audio and the timestamps, and not the audio binary file itself.

And yes, since we have the capability to copy-paste things, of course we can allow copying something or some passage from the library, private from a given song or a given segment of a song. We can copy something and paste it into a given project that we are working on in the private vault so that whenever we paste it, under the hood, what we do is, of course, the clipboard does not keep the audio binary but the audio path so that what we are effectively doing when pasting is copying an audio artifact(s) (it can happen that the selected range spans multiple audio files if we used the re-record option) from a given private library to the personal vault or from the personal vault to the personal vault or from the public library to the personal vault, etc... (maximum flexibility). This is why is very important to find a consensus formatting that is flexible to be ported from any library to another.

## Layer 2: Private Library
As explained this will be the kind of "main" branch for every user privately.
So they will develop, edit and so on in the Personal Vault, which will serve as a way to store projects that are not associated with a given song or artist or that if they are, they are being edited, and when we promote the song from the private vault to the private library we will need to provide some metadata:
- artist
- song name
- version name
This way the user will have its own private library, it will be able to PULL from the public library entire songs with all the metadata there, by ultimately there will be no sync on the metadata, in the sense that whatever metadata we associate in the private library, this only works for that user so whenever this user wants to filter by some metadata field it can do within the private library about their own metadata info but whenever it wants to port the song from private library to the public one it needs to do a PR and fill again all the fields required for the metadata of a new song.

## Layer 3: Public Library
As stated, we will have a review process that the user will need to submit in order to provide a given project the capability to be published publicly in the Songs Public Library under an official Song Name and Artist name (if they don't exist yet, the PR itself will mark that this is a new artist / song name) and of course the user needs to select which version it wants to publish.

Sometimes users may only want to publish the song in the `user_versions/` folder of versions so that this will require a less strict review process, especially if the metadata of the song in the public library it is not modified (some users may not even modify the metadata of a public song because it is already up to date, they simply want to upload a given version, so this is their way of doing it). Once they have it published, then they have the option to ask for their version to become the one pointed at by the **fixed versions** "easy", "medium" or "hard" or a new proposed "version name" the user proposes. So the master user will need to approve this in a different PR, only allowed if the user version in "user_versions" was accepted. 

So overall the PR's are separate:
- PR for changing the metadata of a public song
- PR for adding a new user_version project or editing it (maybe the user wants to edit a given passage because it has enhanced it)
- PR for asking to promote its version as one of the **fixed versions**
